# CLAUDE.md – EasyPDF

## Was ist das?
Plattformübergreifende Desktop-App (Windows, macOS, Linux) zum **Lesen und Neuordnen von PDFs**: horizontaler Lesemodus, Organize-Modus mit Thumbnails und Drag & Drop, Seiten drehen/löschen/einfügen, Dateien verketten, Seiten extrahieren, Dokument teilen. Änderungen passieren zuerst nur im Speicher (Undo/Redo), die Datei ändert sich erst beim Speichern.
**White-Label:** Die App wird pro Unternehmen mit eigenem Namen, Icon, Farben und Herausgeber gebaut (Markenprofile in `branding/<id>/`, Original und Standard: EasyPDF). **Außerhalb von `branding/` nie einen Markennamen schreiben** (Doku/Kommentare: „the app“ bzw. `<App>`, UI-Texte: `{App}`); der Test `BrandingTests.BrandNamesAndWordsStayInTheirProfile` prüft das.

Detaillierter Entwurf, Entscheidungen und UX (auch OCR): **[docs/DESIGN.md](docs/DESIGN.md)** (bei Änderungen am Konzept dort pflegen).

## Tech-Stack
- C# / .NET 11 (`net11.0`), **Avalonia 12** (Fluent-Theme, Skia), CommunityToolkit.Mvvm (MVVM)
- **PDFiumCore 155** (P/Invoke auf pdfium) + `bblanchon.PDFium.*`-Natives für win/linux/osx: Rendern **und** Bearbeiten/Speichern
- Tests: xUnit (Core: xunit 2, App: xunit v3 + Avalonia.Headless.XUnit mit echtem Skia-Rendering)
- .NET-Version an zwei Stellen: SDK in `global.json` (gilt auch für die CI, `setup-dotnet` liest sie), Zielframework `<AppTargetFramework>` in `Directory.Build.props` (alle csproj nutzen `$(AppTargetFramework)`). Wechsel auf eine neuere .NET-Version: beide ändern, sonst nichts.
- **Git-Repository** nur an einer Stelle: `<RepositoryUrl>` in `Directory.Build.props` (das SDK schreibt es in die Assembly-Metadaten → `VersionInfo.Repository` im Info-Dialog; MSI über `DefineConstants`, .deb-Homepage über `build_property`); Markdown verlinkt relativ (`../../releases/tag/latest`), der Workflow nutzt das Repo, in dem er läuft. `RepositoryUrlTests` prüft, dass keine andere Datei die URL nennt.
- **Marke** ([branding/README.md](branding/README.md), Skill `.claude/skills/branding`): `Directory.Build.props` wählt das Profil (`<Brand>`, Standard `easypdf`; überschreibbar mit `-p:Brand=<id>`, Umgebungsvariable `EASYPDF_BRAND` oder `-Brand` der Installer-Skripte; gebaut wird immer nur eine Marke) und importiert `branding/<Brand>/Branding.props` (`$(BrandDir)`). Dort und nur dort stehen: angezeigter Name `<AppDisplayName>` (UI-Texte schreiben `{App}`; bestimmt auch Programmdatei/AssemblyName, Installationsordner, Registry-Schlüssel, Installer-Dateinamen, Benutzerordner, Mutex-/Pipe-Namen, Linux-Paket/-Befehl in Kleinschreibung; im Code `AppInfo.Name` in Core), die zwei Markenfarben `<BrandPrimaryColor>`/`<BrandAccentColor>` (alle Farben Hell/Dunkel und das Icon sind Abstufungen davon: `Styles/BrandColors.cs`, `{st:BrandColor …}` in `App.axaml`; optional `<BrandHeaderColor>` als obere Farbe des Kopfverlaufs), `<Company>`, `<Copyright>`, `<AppAuthor>` (Zeile „Autor“ im Info-Dialog), Installer-Kennungen `<MsiUpgradeCode>`/`<MacBundleId>` (je Marke eigene, nie ändern) und `<BrandWords>`. Icons pro Marke in `branding/<id>/icons/` (erzeugt von `tools/icon/make_icon.py --brand <id>`), Vorstellungsvideos per `branding/<id>/make-presentation-videos.cmd` nach `branding/<id>/videos/` (eingecheckt, werden mit der App ausgeliefert). Technischer Name EasyPDF bleibt für Projekte und Namespaces.
- `Nullable` ist aktiviert und `TreatWarningsAsErrors` an (`Directory.Build.props`): jede Warnung bricht den Build; Version `Major.Minor.Patch.Build`: die ersten drei Teile manuell in `Directory.Build.props` (`<VersionPrefix>`), Build = Anzahl Commits (`Directory.Build.targets`, Target `SetVersionFromGit`; Skripte lesen sie mit `dotnet msbuild src/EasyPDF.App -getProperty:Version -t:SetVersionFromGit`); der Git-Hash steht im Info-Dialog dahinter

## Build, Test, Start, Publish
Ausführlich für Menschen (Voraussetzungen, Installer-Verhalten, CI): [docs/BUILDING.md](docs/BUILDING.md); die READMEs beschreiben nur Funktionen und Anpassbarkeit (bei neuen Funktionen dort ergänzen, beide Sprachen).
```
dotnet build EasyPDF.slnx
dotnet test EasyPDF.slnx                       # Core- und UI-Tests (UI headless, kein sichtbares Fenster)
dotnet run --project src/EasyPDF.App -- "demo-pdfs/Annual Report 2025.pdf"   # 1 PDF: Lesemodus; mehrere PDFs: Verketten-Dialog in dieser Reihenfolge
dotnet publish src/EasyPDF.App -p:PublishProfile=win-x64      # auch linux-x64, osx-arm64 → artifacts/publish/<rid>/
pwsh installer/windows/build-windows-on-windows.ps1                 # MSI (WiX v5 per NuGet) → artifacts/installer/
pwsh installer/linux/build-linux-on-linux.ps1                      # nur unter Linux (Native AOT): .deb + .tar.gz (ohne dpkg)
bash installer/build-macos-on-macos.sh                              # nur auf einem Mac: .app (ad hoc signiert) + .dmg
```
Der Name der Installer-Skripte sagt, auf welchem System sie gestartet werden (`build-<Ziel>-on-<System>`: `build-windows-on-windows`, `build-linux-on-linux` (pwsh), `build-macos-on-macos`, letzteres auch auf GitHub Actions; Native AOT baut nur für das System, auf dem es läuft, und braucht dessen C-Toolchain: Windows C++-Build-Tools von Visual Studio (das Skript prüft sie vorab), Linux `clang` + `zlib1g-dev`, macOS Xcode-Kommandozeilenwerkzeuge). Die `installer/*/build-*.ps1`-Skripte (und `build-macos-on-macos.sh`) holen zuerst den neuesten Stand (`installer/update-sources.ps1`: `git pull --ff-only` auf dem aktuellen Branch; nicht auf CI und bei losgelöstem HEAD; kamen neue Commits, startet das Skript neu; `-NoPull` bzw. `EASYPDF_NO_PULL=1` überspringt es; scheitert der Pull, bricht der Build ab). Dann zeigen sie die gewählte Marke als `-p:Brand=<id>` an (`installer/selected-brand.ps1`, in `build-macos-on-macos.sh` eigener Code) und geben den Parameter an jeden Build-Befehl weiter. Marke als Parameter: `-Brand <id>`, `-p:<id>`, `-p:Brand=<id>` oder nur `<id>`; unbekannte Parameter brechen ab. Danach löschen sie immer alle `bin/`/`obj/` (`installer/clean-build-output.ps1`, `git clean -fdX src tests installer`; `build-macos-on-macos.sh` macht es selbst, auf dem Mac ist kein PowerShell nötig) → jeder Installer ist ein kompletter Neubau. Danach laufen alle Tests (`installer/run-tests.ps1`, `dotnet test EasyPDF.slnx`; macOS-Skript selbst); ein roter Test bricht den Build ab, `-NoTests` bzw. `EASYPDF_NO_TESTS=1` überspringt sie (im Workflow laufen sie nur im Windows-Job). Nach erfolgreichem Build räumen sie nochmal auf (`clean-build-output.ps1 -Intermediate`: `bin/`/`obj/` sowie `artifacts/publish` und `artifacts/macos`), sodass nur `artifacts/installer` bleibt; nicht auf CI (der Upgrade-Test baut das MSI aus `artifacts/publish` neu). Der `.cmd`-Starter `installer/build-windows-on-windows.cmd` ruft die gleichnamige `.ps1` in `installer/windows/` auf, öffnet nach erfolgreichem Build `artifacts/installer` im Explorer und schließt sich; nur bei Fehler wartet er (`PAUSE`). Die `.ps1` öffnen keinen Explorer (wegen CI).
Die Publish-Profile bauen **Release mit Native AOT** (alle Installer und die portable Windows-`.zip`; native Debug-Symbole `.pdb`/`.dbg`/`.dSYM` löschen die Skripte vor dem Packen); alle Installer-Skripte und der CI-Workflow nutzen sie, Debug-Builds sind davon nicht betroffen.
Testdatei: `demo-pdfs/Annual Report 2025.pdf` (Jahresbericht einer erfundenen Energiegenossenschaft, alle Namen und Zahlen erfunden; 19 Seiten, 74 KB, keine Lesezeichen; selbst erzeugt mit `python tools/demo-pdf/make_demo_pdf.py`, im Docstring steht, was Tests davon brauchen: Titelblatt mit Bild und Schmuckfarbe, Inhaltsverzeichnis mit Punktreihen, Text, Tabellen, Diagramme, Querformatseite mit Karte).
Test-PDFs mit Lesezeichen/verschiedenen Seitengrößen werden in den Tests von Hand geschrieben (pdfium kann keine Bookmarks erzeugen).

## Architektur-Notizen
- **pdfium ist nicht thread-sicher**: *alle* pdfium-Aufrufe laufen auf dem einen Thread von `PdfiumWorker` (Prioritäts-Queue, abbrechbar). Rendering liefert BGRA-Puffer, die UI-Schicht macht daraus `WriteableBitmap`s.
- **Laden**: `PdfSource` öffnet per `FPDF_LoadCustomDocument` + `FileStream` (blockweise, Datei wird nicht komplett geladen). **Wichtig:** das Callback-Delegate muss als Feld gehalten werden, sonst sammelt der GC es ein → Absturz (Regressionstest `SurvivesGarbageCollection`). Gilt auch für Schreib-Callbacks.
- **Dokumentmodell**: `EditableDocument` hält eine unveränderliche Seitenliste (`PageEntry`: Quelle, Quellseite, Zusatzrotation) pro Zustand; Undo/Redo tauscht Snapshots. Operationen: Move/Rotate/Delete/InsertFrom, `Combine` (Concatenate).
- **Speichern** (`PdfSaver`): arbeitet auf einer frischen Kopie der Basisdatei (bleibt Bookmarks/Metadaten erhalten), importiert Seiten fremder Dateien, löscht entfernte, ordnet per `FPDF_MovePages`, setzt Rotation, schreibt in Temp-Datei und ersetzt dann; danach wird die Datei neu geöffnet (Verlauf wird geleert). Extract/Split erzeugen neue Dokumente (ohne Bookmarks). **Schwärzen/Abdecken** (`PageRedactor`) entfernt beim Speichern alles unter den Boxen endgültig (berührte Objekte raus, sichtbarer Rest als Bild + unsichtbarer Text zurück); Dokumente mit Boxen schreibt pdfium ein zweites Mal, weil es in der Sitzung neu erzeugte Objekte sonst auch unbenutzt mitschreibt (Details DESIGN.md „Black out / white out“).
- **Lesemodus** (`HorizontalPageView`): Layout/Zoom in `HorizontalLayout` (reine Mathematik, getestet); Rendering nur sichtbarer Seiten + 2 Nachbarn, LRU-Cache mit Byte-Budget; Zoom um die Mausposition; ist die Ansicht verdeckt, behält sie Layout und Position.
- **Organize** (`ThumbnailGrid`): eigene Zeichnung, Auswahl über Seiten-IDs (`PageEntry.Id`, im ViewModel gehalten), Drag & Drop per Zeiger-Ereignissen; Änderungen laufen über Events (`SelectionRequested`, `MoveRequested`) zum ViewModel.
- **Seiten-Randleiste** im Lesemodus: dasselbe `ThumbnailGrid` mit `IsNavigator=True` (keine Auswahl/Drag & Drop; `ActivePage` = gelesene Seite wird markiert und eingeblendet, Klick → `PageClicked` → `MainViewModel.GoToPage`).
- **Befehle**: einmal in `MainViewModel` definiert; Menüleiste (`NativeMenu`, auf macOS global), Tastenkürzel, Ribbon und Kontextmenüs binden dieselben Commands (Tabelle `Entry` in `MainWindow.axaml.cs`). Kontextmenü (Rechtsklick auf Seite) ist in beiden Modi identisch.
- **Mehrere Dokumente = mehrere Fenster** in *einem* Prozess: `WindowManager` (`Services/`, implementiert `IDocumentWindows`) hält alle `MainWindow`s (je eigenes `MainViewModel`, gemeinsames `AppSettings`). Regel: Datei öffnet im aktuellen Fenster, wenn es leer ist, sonst in einem neuen; eine Datei, die schon Dokument eines Fensters ist, holt dieses nach vorn. Ohne `IDocumentWindows` (ViewModel-Tests) ersetzt das ViewModel sein Dokument direkt. „Schließen“ schließt bei mehreren Fenstern auch das Fenster, „Beenden“ alle.
- **Kontextmenü/Start mit Dateien**: `Program.Main` → `StartupArguments` (`[--merge | --read] dateien…`; `--read` = jede Datei in einem eigenen Fenster); bei `--merge` sammelt `MergeInstances` (benannter Mutex + Named Pipe) die Dateien parallel gestarteter Prozesse ein (Explorer startet pro markierter Datei einen), nur der erste zeigt den Verketten-Dialog. Danach gibt `InstanceChannel` (eigener Mutex + Pipe, nur aktueller Benutzer) die Anfrage an einen schon laufenden Prozess weiter und beendet sich; dort verteilt `WindowManager.OpenFilesAsync` sie auf die Fenster. Beide Pipes übertragen eine Nachricht, die der Empfänger mit einem Byte bestätigt (`PipeMessage`; unter Linux/macOS sind Pipes Unix-Sockets, ohne Bestätigung gingen Übergaben verloren). macOS liefert Finder-Dateien als `FileActivatedEventArgs` (App.axaml.cs). Registry-Einträge im MSI (`Package.wxs`), Dolphin/Nemo-Menüs in `installer/linux/filemanager/`.
- **Aussehen** (Hausstil: dunkle Primärfarbe, helle Akzentfarbe der Marke, Schrift Barlow für alle Marken): Farben nur als Rollen-Ressourcen in `App.axaml` (Hell/Dunkel), keine festen Farben in Views/Controls; Styles in `Styles/Controls.axaml` und `Styles/Ribbon.axaml`. Details: DESIGN.md „Look“. Screenshots zum Prüfen: `EASYPDF_SCREENSHOTS=<Ordner> dotnet test … --filter ScreenshotTests`.
- **Lokalisierung**: `{loc:Tr Key}` bindet an `LocString` (aktualisiert live beim Sprachwechsel – Indexer-Bindings tun das in Avalonia nicht). Im Code `Loc.T("Key")` / `Loc.F("Key", args)`.

## Conventions
- **Keine Rückwärtskompatibilität nötig, solange nicht ausdrücklich angefordert:** Also keine Erkennung oder Migration alter Versionen, Namen, Einstellungen, Registry-Schlüssel oder Dateiformate und keine Aufräum-Logik für alte Installationen. Updates der aktuellen Version (MSI-`UpgradeCode`, neuere Version ersetzt ältere) bleiben erhalten.
- Code comments: English. Identifiers: English. Commit messages: English. Chat replies may be in English.
- **Docs: English.** Only the top-level README also exists in German (`README_DE.md`, keep both in sync); everything else (`docs/`, `branding/`) is English only.
- **UI language: English + German.** Every new UI string goes into **both** `Strings.resx` and `Strings.de.resx` (a test checks completeness, placeholders and that every used key exists). No string concatenation for sentences – use format placeholders (`{0}`).
- Dialog-Ergebnisse so definieren, dass „Fenster mit [X] schließen“ = Abbrechen ist (z. B. `UnsavedChoice.Cancel` ist der Default-Wert).
- UI-Tests: Neue UI-Funktionen bekommen Headless-Tests (`[AvaloniaFact]`, Maus/Tastatur per `window.MouseDown/KeyPress`); zwei schnelle Klicks auf dieselbe Stelle gelten als Doppelklick.
- Nach jedem Arbeitsschritt: Build + Tests grün, Commit, Push, dann in die Release-Repos übernehmen (nächster Abschnitt).

## Repositories und Ablauf
Details: [docs/BUILDING.md](docs/BUILDING.md) „Development and release repositories“.
- **Entwickelt wird nur im Entwicklungs-Repo auf `main`**; es gibt keine Marken-Branches.
- **Release-Repos:** je veröffentlichter Marke eines, als Klon neben dem Entwicklungs-Repo (Ordner heißt wie der angezeigte Name der Marke; steht in `branding/<id>/README.md`). Sie unterscheiden sich von `main` nur durch die eigene `<RepositoryUrl>` und, wenn ihre Marke nicht `easypdf` ist, durch die Standardmarke (`<Brand>` in `Directory.Build.props` und die Stellen, die den Standard nennen: `CLAUDE.md`, `README.md`, `README_DE.md`, `branding/README.md`, `.claude/skills/branding/SKILL.md`).
- **Übernehmen** nach jedem Commit auf `main`, in jedem Release-Repo: `git fetch <Entwicklungs-Repo> main`, `git cherry-pick -x <zuletzt>..FETCH_HEAD`, `git push origin main`. `<zuletzt>` = Hash aus der Zeile `(cherry picked from commit …)` des neuesten Commits dort. Bei Konflikten in den genannten Dateien Adresse und Standardmarke des Release-Repos behalten. Vor dem Push prüfen: `git diff --stat FETCH_HEAD HEAD` zeigt nur die genannten Dateien.
- In den Release-Repos nie direkt arbeiten und **nie Force-Push**: jede Änderung soll dort als eigener, normaler Commit nachvollziehbar sein.
